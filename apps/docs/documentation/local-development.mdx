## Introduction

Stair-Doc's codebase is set up in a monorepo (via [Turborepo](https://turbo.build/repo)).
Here's the monorepo structure:

```
apps
├── api       FastAPI backend
├── docs      Mintlify documentation
├── web       Next.js PWA frontend
packages
├── eslint-config
├── typescript-config
```

The `apps` directory contains:

- `web` — The Next.js 15 PWA control dashboard
- `api` — The FastAPI backend (Python 3.10+) for robot telemetry and delivery management
- `docs` — This Mintlify documentation site

The `packages` directory contains shared ESLint and TypeScript configs generated by `create-turbo`.

## Running Stair-Doc locally

### Step 1: Local setup

<Steps>
  <Step title="Clone the repo">
    Clone the repository:

    ```bash
    git clone https://github.com/cording12/next-fast-turbo.git stair-doc
    cd stair-doc
    ```

  </Step>
  <Step title="Install Node.js dependencies">    
    From the root directory, install all workspace dependencies:

    ```bash
    pnpm install
    ```

  </Step>

  <Step title="Open the VS Code workspace">
    Open the pre-configured workspace for the best developer experience (correct Python interpreter, named terminals, task runner integration).

    Navigate to `.vscode/` and double-click `next-fast-turbo.code-workspace`, or in VS Code choose **File → Open Workspace from File**.

    <Tip>You can rename the `.code-workspace` file to match your project name — just keep the `.code-workspace` extension.</Tip>

  </Step>
</Steps>

### Step 2: Python setup

<Note>
  In a monorepo, VS Code sometimes uses the wrong Python interpreter, leading to
  **module not found** errors. You can open the `api` folder in its own VS Code
  window, but using the pre-configured Workspace is recommended.
</Note>
While working on the Python backend, ensure that your terminal is activated in
the correct folder. From the root, run the following command to change to the
`api` directory:

```bash
cd apps/api
```

<Steps>
  <Step title="Create a virtual environment">
    Create a virtual environment in the `api` directory:

    <CodeGroup>
    ```bash Poetry
    poetry install
    ```

    ```bash Pip
    python -m venv .venv
    ```
    </CodeGroup>

<Tip>
  If you're using Poetry, you could receive an error noting incorrect format of
  the `poetry.lock` file. This is a version mismatch between the version
  installed and the version used to generate the lock file. You can fix this by
  deleting the `poetry.lock` file and running `poetry install` again.
</Tip>

  </Step>
  <Step title="Install dependencies (if not using Poetry)">    
    Run the following command to install the Python dependencies:

    ```bash
    pip install -r requirements.txt
    ```

  </Step>

  <Step title="Create the .env file">
    Create a `.env` file inside `apps/api/` with the following variables:

    ```env
    # Supabase database
    DB_URL=https://your-project.supabase.co
    DB_API_KEY=your-supabase-anon-key
    DB_EMAIL=your-supabase-email
    DB_PASSWORD=your-supabase-password

    # JWT authentication
    JWT_SECRET_KEY=change-me-min-32-chars-for-production

    # Deployment (leave empty for local dev)
    ROOT_PATH=
    ```

    <Warning>
      Never commit a real `JWT_SECRET_KEY` or Supabase credentials to source
      control. Use a `.env.example` file with placeholder values instead.
    </Warning>

  </Step>
</Steps>

### Step 3: Supabase database setup

Stair-Doc uses [Supabase](https://supabase.com/) as its PostgreSQL database.

<Steps>

<Step title="Create a Supabase project">
  Visit [supabase.com](https://supabase.com) and create a free account and a new
  project.
</Step>

<Step title="Copy API credentials">
  From the project dashboard, copy the **Project URL** and **anon public API
  key** and paste them into your `.env` file.
</Step>

  <Step title="Create the required tables">
    In the Supabase **Table Editor**, create the following tables:

    | Table | Key columns |
    |-------|-------------|
    | `users` | `id` (uuid PK), `name`, `email`, `hashed_password`, `role` (`operator` / `recipient` / `admin`), `floor_access` (int[]), `rfid_tags` (text[]) |
    | `deliveries` | `id` (uuid PK), `robot_id`, `recipient_id`, `rfid_tag_id`, `pickup_floor`, `dropoff_floor`, `status`, `created_at`, `updated_at` |
    | `rfid_tags` | `id` (uuid PK), `tag_id`, `assigned_to` (user id FK), `is_active` |
    | `camera_images` | `id` (uuid PK), `delivery_id`, `image_url`, `captured_at` |

    <Warning>
      Row-Level Security (RLS) is disabled by default for development convenience. Enable RLS and add appropriate policies before deploying to production.
      See the [Supabase RLS docs](https://supabase.com/docs/guides/auth/row-level-security).
    </Warning>

  </Step>

  <Step title="Seed initial users">
    Use **Table Editor → Insert rows** to create at least one admin user, or call the `/api/v1/auth/register` endpoint directly.

    Demo credentials for local testing:

    | Email | Password | Role |
    |-------|----------|------|
    | `operator@stairdoc.com` | `password123` | operator |
    | `recipient@stairdoc.com` | `password123` | recipient |
    | `admin@stairdoc.com` | `password123` | admin |

  </Step>

</Steps>

### Step 4: Configure Turbo remote caching (optional)

Turborepo can use a technique known as [Remote Caching](https://turbo.build/repo/docs/core-concepts/remote-caching) to share cache artifacts across machines, enabling you to share build caches with your team and CI/CD pipelines.

By default, Turborepo will cache locally. To enable Remote Caching you will need an account with Vercel.

<Steps>
  <Step title="Login via Turborepo CLI">
    From the project root, run the command: ```bash npx turbo login ``` This
    will authenticate the Turborepo CLI with your [Vercel
    account](https://vercel.com/docs/concepts/personal-accounts/overview).
  </Step>
  <Step title="Link your Turborepo to your Remote Cache">
    Link your Turborepo to your Remote Cache by running the following command
    from the root of your Turborepo: ```bash npx turbo link ```
  </Step>
</Steps>

### Step 5: Frontend environment

Create a `.env.local` file inside `apps/web/`:

```env
NEXT_PUBLIC_API_URL=http://localhost:8000
NEXT_PUBLIC_SOCKET_URL=http://localhost:8000
NEXT_PUBLIC_ENABLE_TELEMETRY=true
NEXT_PUBLIC_ENABLE_RFID=true
```

### Step 6: Run everything

From the repo root, start the frontend, backend, and docs site together:

```bash
pnpm run dev
```

| Service            | URL                        |
| ------------------ | -------------------------- |
| Next.js dashboard  | http://localhost:3000      |
| FastAPI backend    | http://localhost:8000      |
| API docs (Swagger) | http://localhost:8000/docs |
| Mintlify docs      | http://localhost:3001      |

<Tip>
  You can still run each app individually from its own directory using `pnpm run
  dev`.
</Tip>

## Working with the monorepo in VS Code

VS Code Workspaces solve the Python virtual environment problem in monorepos and give you named terminals and tasks for each package.

<Note>
  For a detailed guide on multi-root workspaces, see the [official
  documentation](https://code.visualstudio.com/docs/editor/multi-root-workspaces).
</Note>

### Open the workspace

In `/.vscode/` open `next-fast-turbo.code-workspace`. This gives you separate root folders for `web`, `api`, and `docs` in the Explorer sidebar.

### Step 2: Running tasks

VS Code will try to autodetect tasks from gulp, grunt, npm, and TypeScript project files across all folders in a workspace as well as search for tasks defined in tasks.json files. The location of tasks is indicated by a folder name suffix

<Frame caption="Workspace tasks">
  <img src="/_images/tasks.png" />
</Frame>

From the above example, you can see there are several configured tasks with the relevant folder name after the task name.

### Step 3: Debugging

With multi-root workspaces, VS Code searches across all folders for `launch.json` debug configuration files and displays them with the folder name as a suffix.
Additionally VS Code will also display launch configurations defined in the workspace configuration file.

<Frame caption="Run and debug panel">
  <img src="/_images/run-and-debug.png" />
</Frame>

You can still create [launch configurations](https://code.visualstudio.com/docs/editor/debugging#_launch-configurations) for each individual package in the monorepo and they will populate in the dropdown list automatically.

#### Workspace launch configurations

Add a compound launch config to `next-fast-turbo.code-workspace` to start the full stack with one click:

```json
{
  "launch": {
    "version": "0.2.0",
    "configurations": [],
    "compounds": [
      {
        "name": "Stair-Doc: Full Stack",
        "configurations": ["Next.js: Chrome", "Python: FastAPI"]
      }
    ]
  }
}
```

For a more detailed explanation, check out the [official documentation](https://code.visualstudio.com/docs/editor/multi-root-workspaces#_workspace-launch-configurations)

  </Accordion>
  <Accordion title="Workspace Terminals (recommended)">
    <Frame caption="Workspace Terminals in VS Code">

    </Frame>

      [Workspace Terminals](https://marketplace.visualstudio.com/items?itemName=joshx.workspace-terminals)

  </Accordion>
</AccordionGroup>
